## Summary

Three things landed, none needing a new dependency or any network:

1. `src/causalmesh/adapters/x402_pay.py`: the operator-facing half of x402.
   A `PaymentSigner` protocol the operator implements, an injected `send`
   callable that makes the real HTTP retry, and `pay_if_allowed(...)`, which
   decides through the gate, refuses as data, calls the operator's code only
   when allowed, and records spend with reserve-then-commit so a failure after
   money may have left is counted as `unknown`, never as zero. A SQLite
   `PaymentJournal` provides the idempotency guard and counts in-flight
   payments against the budget atomically (`BEGIN IMMEDIATE`).

## CHANGELOG bullets

- Added `causalmesh.adapters.x402_pay`: `pay_if_allowed`, `PaymentSigner`
  (protocol), `PaymentResponse`, `PaymentNotSent`, `PaymentOutcome`,
  `PayStatus`, `PaymentJournal`. The library holds no wallet or key, adds no
  dependency, and never makes the network request; the operator injects the
  signer and the HTTP-retry callable.
- x402 payments are recorded reserve-then-commit. A signer or `send` failure
  other than an explicit `PaymentNotSent` is recorded as an `unknown` outcome
  and counted at full amount against the budget; only a 2xx response is
  `paid`, and a repeat 402 is `rejected` (not recorded).
- x402 payments carry a caller-supplied idempotency key. A replay never
  reaches the signer while the first attempt is in flight, paid or unknown;
  concurrent duplicates pay once.
- Payments in flight count against the declared `usd_total` atomically with
  the reservation, so concurrent payers cannot overspend together.
- Added `docs/preregistration-draft.md` (draft, unsigned; owner decisions
  listed as TODO, none answered) and `docs/staleness-estimators-needed.md`
  (requirements only; no estimator).

Add:

### The ledger cannot reverse an unconfirmed payment

**Status: not built.** An `unknown` x402 payment is recorded to the append-only
`Ledger` at full amount (over-counting is the safe direction). If an operator
later confirms via `PaymentJournal.resolve(..., paid=False)` that no money
moved, the journal makes the key retryable but the ledger entry stays, so the
budget stays over-counted. **What it would take:** an adjustment or void entry
in `policy/ledger.py` that `Ledger.total` honours, without weakening the
"every entry is an action that happened" rule.

### A killed process leaves an x402 payment `reserved`

**Status: accepted limit.** `pay_if_allowed` is not a transaction with the
payment network. A process killed between the operator's money leaving and the
journal commit leaves a `reserved` row. It stays counted against the budget and
blocks the same idempotency key until an operator settles it with
`PaymentJournal.resolve`. There is no automatic expiry, because an expiry would
un-count money that may have moved. Nothing lists stale `reserved` rows in the
CLI yet.

### The confirmatory design has two plannable tasks, not four

**Status: found while drafting the preregistration.** `Profile.run_count(4) ==
1920` is tested, but `tasks/` holds three definitions and `_build_plan`
(`cli/commands_experiment.py`) excludes the CooperBench import, so
`experiment plan --profile confirmatory --allow-gated` would plan 960 runs.
See `docs/preregistration-draft.md` sections 1.1 and TODO-TASKS.

### Repetitions under the mock agent may be replicates

**Status: to verify empirically, not asserted.** `agents/mock.py` is
deterministic and nothing in `agents/` consumes `identity.seed`, so 120
repetitions of a (task, arm) cell may be identical runs; the effective sample
size would then be the number of cells. A pilot comparison of repeated cells
would settle it. See `docs/preregistration-draft.md` 1.6 and TODO-POWER.

### Per-turn injection counts are not persisted; observation keys differ

**Status: instrumentation gap, recorded for the staleness work.**
`InjectionAccounting` keeps running totals and a per-turn digest only; per-turn
`events_injected` / `events_dropped` are transient. Also the scripted agent
writes `observations[].event_ids` while `ModelAgent` writes
`observations[].events`, so a loader reading one key reports nothing for the
other. See `docs/staleness-estimators-needed.md`, sections 3.2 and 3.3.

```python
from causalmesh.adapters.x402 import parse_payment_required
from causalmesh.adapters.x402_pay import (
    PaymentJournal, PaymentResponse, PaymentNotSent, pay_if_allowed,
)

class MySigner:                      # you write this; the library never signs
    def sign(self, requirement, *, x402_version):
        return my_scheme_specific_header_value(requirement)

def send(headers):                   # you make the HTTP retry; the library never does
    r = my_http.get(url, headers=headers)
    return PaymentResponse(r.status_code, dict(r.headers), r.content)

outcome = pay_if_allowed(
    parse_payment_required(headers=resp.headers, body=resp.content),
    gate=gate, ledger=ledger, journal=PaymentJournal("data/x402.db"),
    signer=MySigner(), send=send, agent_id="buyer",
    idempotency_key="order-123", now_us=now_us,
)
if outcome.money_may_have_moved:     # True for "paid" and for "unknown"
    ...
```

Statuses: `paid` (2xx, recorded), `unknown` (failure after money may have left,
recorded at full amount), `rejected` (server answered 402 again, not recorded),
`not_sent` (your code raised `PaymentNotSent`, not recorded), `refused` (gate or
in-flight budget said no; your code was never called), `duplicate` (idempotency
key already used; your code was never called). Raise `PaymentNotSent` only when
you know nothing left; any other exception is treated as `unknown`.

Not verified against any real facilitator; do not describe this as
production-ready.
